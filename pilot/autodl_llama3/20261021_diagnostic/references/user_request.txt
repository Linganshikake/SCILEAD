## 三、首先解决结构化输出问题

之前的单篇测试：

- 输入 4,226 Tokens
- 输出 205 Tokens
- 正常遇到 EOS
- 输出存在解释性前缀
- Result 字段出现数值类型
- 不能作为合法的完整 JSON 直接解析

请先检查：

1. 作者源码如何处理 Llama-3 生成文本。
2. 作者 README 是否允许格式整理，以及具体处理边界。
3. 原版 Prompt 与 Hugging Face Pipeline 的实际输入是否完全一致。
4. 已有 `author_hf_pipeline.py` 是否正确恢复作者原版的输出包装行为。
5. JSON 解析失败究竟来自输入重复拼接、提示模板、输出前缀，还是模型生成的内容。
6. Result 字段的预期类型以及官方后处理逻辑。
7. tokenizer、特殊 token、EOS、max_new_tokens 与作者配置是否一致。

重点：

之前已观察到的格式错误，不能仅通过正则表达式随意提取并修改后直接算作正式实验结果。

如果官方方法存在明确的格式纠正规则，可按原版规则执行，并保存原始与处理后的内容。

如果需要自行增加格式处理，则先在独立诊断目录实现一个候选方案，仅允许可验证的纯语法处理，例如移除唯一 JSON 对象之外的说明性前缀，或按明确规则进行类型序列化。

不得改变任何 Task、Dataset、Metric、Result 的实际含义，不得补充记录或更换实验结果。

请生成格式诊断报告，逐项说明：

- 原始输出是否可解析；
- 是否存在唯一、完整的 JSON 记录结构；
- 处理前后字段是否完全一致；
- 是否需要新增官方方法之外的操作；
- 哪些情况只能保留为解析失败。

若正式运行需要引入作者方法未定义的格式纠正规则，先向我提交规则及具体示例，获得确认后再使用。
